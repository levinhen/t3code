## Fork: desktop app

- `main` is the fork's working branch (tracks `origin/main`; `upstream/main` is pingdotgg). Land fork features on `main` and build Fork packages from it.
- Fork schema changes go in `apps/server/src/persistence/ForkMigrations/`, registered in `forkMigrations.ts` (its own `fork_sql_migrations` ledger, run after upstream's). Never add a numbered file to `Migrations/`: upstream keeps numbering past the fork's base, and the migrator skips every id up to the highest recorded, so a fork id there blocks upstream's next migrations on the live database. Fork migrations never redefine an upstream table or index: give fork reads their own `fork_`-named index, so upstream can rebuild its indexes across rebases without a merge. `scripts/fork-move-migrations.sh`, which the install script runs first, moves any numbered migration the fork added to `Migrations/` into the fork ledger under the next fork id and leaves the move for you to commit.
- `scripts/fork-desktop-install.sh` builds this checkout and installs it as `/Applications/T3 Code (Fork).app` (`com.t3tools.t3code.fork`) beside the official app. Run it on the Mac. Without Rust it reuses the official app's resource monitor; it backs up `~/.t3/userdata/statev2.sqlite` to `~/.t3/backups` before installing. If the Fork app is running, the script builds and then waits for it to quit before replacing it, so run it from Terminal (quitting the app ends any agent session inside it).
- `scripts/fork-sign.sh <app>` signs with a self-signed identity kept in `~/.config/t3code-fork-signing` (created on first use). The install script calls it. Builds keep the same signing requirement, so Keychain "Always Allow" and macOS privacy grants carry over to later builds; deleting that keychain costs one more prompt. Never re-sign a running app.
- Both apps share `~/.t3/userdata` and the Electron profile, so only one runs at a time.
- A dev server (`vp run dev`) can start under the `mac` runner's sandbox (using `~/.t3/dev` or the worktree's `.t3`, never `~/.t3/userdata`): `/bin/ps` is allowed, and blocked reads of `~/.claude` / `~/.claude.json` / `~/.codex` only log non-fatal provider/telemetry warnings (the "Replay (dev)" provider works without them).
- `scripts/fork-backup.sh install` sets up a launchd job that copies `statev2.sqlite` to `~/.t3/backups/daily` at most once a day, keeping 7. `uninstall` removes it. The `mac` runner can write `~/Library/LaunchAgents/local.t3code-*.plist` and run `launchctl bootout` (`uninstall` works), but `launchd` blocks `launchctl bootstrap` from inside any Seatbelt sandbox (`Input/output error`), so `install` (loading the job) still needs to run from Mac Terminal. To restore, quit T3 Code, delete `statev2.sqlite-wal` and `statev2.sqlite-shm` (a stale WAL would be replayed onto the restored file), then copy a backup over `statev2.sqlite`.
